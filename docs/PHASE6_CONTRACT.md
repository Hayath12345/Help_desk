# Phase 6 — AWS readiness: build contract (binding)

Scope (spec `docs/BUILD_SPEC.md` §4 and §14.6): **prepare, do not deploy.** Dockerfiles for `web`, `api` and `worker`;
production environment configuration for RDS (PostgreSQL), ElastiCache (Redis), S3, SES and SNS; migrations run on
deploy; health checks; a deployment guide in the README. **Done when:** the three images build from a clean checkout,
start against the local Docker services with a production-style configuration, pass their health checks, and a
fresh database is brought to the current schema by the documented deploy step (automated smoke script + the checks
below). Nothing is pushed to a registry or deployed to AWS.

Out of scope: creating AWS resources (no Terraform/CloudFormation unless it is small, optional and clearly marked as an
example), CI/CD pipelines, a real virus scanner, a real Entra ID / Google tenant, load testing.

Read first: `docs/PHASE2_HANDOFF.md` (Deployment notes: S3 lifecycle JSON, IAM, sockets), `docs/PHASE3_HANDOFF.md`,
`docs/PHASE4_HANDOFF.md`, `docs/PHASE5_HANDOFF.md`, README ("Deployment notes"), `.env.example`, `apps/api/src/config.ts`,
`apps/web/next.config.ts` (standalone output), `apps/web/AGENTS.md`.

## Decisions (made for the owner — "what you deem fit"; each can be overridden later)

| #   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| G1  | **Three images from one multi-stage build file per app** (`apps/web/Dockerfile`, `apps/api/Dockerfile` with a `worker` target that differs only in its command), built from the repository root as the context. Base: the official `node:24-bookworm-slim` (Node ≥ 24.16 is required; pin the minor in the file and in the guide), non-root user, `tini`/`--init` style signal handling, `NODE_ENV=production`, no dev dependencies, no `.env`, no source maps of secrets, `.dockerignore` at the root. Images are reproducible: `pnpm install --frozen-lockfile`, the pnpm version from `packageManager`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| G2  | **Web** runs the Next.js **standalone** server (already configured), static assets copied next to it as `next start` docs describe; listens on `0.0.0.0:3000`; `HOSTNAME`/`PORT` set. Build-time `NEXT_PUBLIC_*` values are documented (they are baked in at build: API URL, upload origin) and passed as build args.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| G3  | **API and worker** run the same code (`src/server.ts`, `src/worker.ts`). Prefer a pruned production install (`pnpm deploy`) over copying the whole monorepo; if the code must run through `tsx` (no compile step exists today), say so in the guide and keep `tsx` as a production dependency of `@loons/api`; compiling to JavaScript is allowed only if it is small, tested and does not change behaviour. Prisma client is generated at build; the **Prisma CLI is not in the runtime images** — migrations run from a separate `migrate` image/target (G5).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| G4  | **Health checks:** the API already has `GET /health` (readiness: database + Redis) and `GET /health/live`. Add: container `HEALTHCHECK`s for api (live), web (a cheap page, not the log line — the web server prints Ready before its config check, see README) and worker (a lightweight liveness mechanism: e.g. the worker writes a heartbeat key/file or exposes a tiny internal health port; choose the simplest that works behind an ECS/Kubernetes health check and document it). `/health` must report the app version (already does) and never leak secrets.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| G5  | **Migrations on deploy:** a `migrate` target/image (Prisma CLI + migrations only) whose command is `prisma migrate deploy`, intended as a one-off task before the new api/web/worker start (ECS run-task / Kubernetes Job / `docker compose run`); idempotent; documented failure behaviour (the old version keeps serving; never `migrate dev`/`reset` in production). The seed for **production** (`db:seed` with `NODE_ENV=production`, configuration only, no demo data) is a second documented one-off.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| G6  | **Production configuration:** `.env.production.example` (every variable, grouped, with the AWS value or the secret source for each; no real secrets) and a startup **configuration check** that already refuses placeholders — extend it with production-only rules where missing (HTTPS URLs, `SOCKET_REDIS_ADAPTER=true` when more than one instance is declared, `TRUSTED_PROXY_HOPS ≥ 1`, `EMAIL_PROVIDER=ses`/`SMS_PROVIDER=sns`/`TEAMS_PROVIDER=webhook` allowed values, S3 without a custom endpoint, TLS for the database and Redis URLs). Secrets come from the environment (AWS Secrets Manager / SSM Parameter Store injection by the orchestrator); the guide lists which variables are secrets.                                                                                                                                                                                                                                                                                                                                                                                                     |
| G7  | **Providers:** verify the SES email provider, the SNS SMS provider, S3 (IAM role / default credential chain, no static keys) and the `rediss://` TLS path are implemented and covered by tests with mocked AWS clients; fix gaps found. No call to real AWS in tests.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| G8  | **Region and endpoints configurable** (expected `me-central-1` or `me-south-1`): every AWS client takes its region from configuration; SES/SNS availability per region is noted in the guide (with the fallback to another region's endpoint for SMS/SES if the chosen region lacks the service — as a documented choice, not code magic).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| G9  | **Deployment guide** in the README (or `docs/DEPLOYMENT.md` linked from it): architecture diagram (text/ASCII or Mermaid), the AWS building blocks (ALB with websocket support and idle timeout, ECS Fargate or EKS services web/api/worker, RDS, ElastiCache, S3 with the lifecycle rule and CORS, SES identities/DKIM, SNS SMS, Secrets Manager/SSM, CloudWatch logs/alarms), networking and security groups, the IAM policy for the API/worker task role (least privilege, exact actions already in `PHASE2_HANDOFF.md` plus SES/SNS), environment variables table (secret vs plain), the step-by-step first deployment and the upgrade procedure (build → push → migrate → roll web/api/worker), rollback, scaling notes (sockets per instance, Redis adapter, worker count and `WORKER_SCHEDULERS` on exactly one instance), backup/retention (RDS snapshots, S3 versioning stance), monitoring/alarms, cost-relevant knobs, and a go-live checklist (Entra ID, Google OAuth, SES production access, SNS SMS spend limit/sandbox, virus-scan hook, MFA via Conditional Access, domain/DNS/TLS certificate). |
| G10 | **Local production-style rehearsal:** `docker-compose.prod.yml` (an example, clearly named; not the dev compose) that runs the three images + migrate job against the local postgres/redis/minio/mailpit with production-style env, and `scripts/smoke-prod.sh` (or an npm script) that builds the images, starts them and waits for health. The dev-only staff password form is disabled in production mode, so the smoke does not sign in; it checks `/health`, `/health/live`, the web login page, a Socket.IO handshake rejection without a token, and that the migrate job leaves `prisma migrate status` clean on an empty database. Rehearsal data is created in its own database/bucket/Redis prefix and removed afterwards.                                                                                                                                                                                                                                                                                                                                                                             |
| G11 | **Security review of the packaging:** images contain no `.env`, no test files, no design prototype, no secrets in layers or build args other than `NEXT_PUBLIC_*`; non-root; read-only root filesystem works (writable `/tmp` only); `npm audit`-style check of the production install is reported (not enforced); headers/CSP in production mode verified (`security-headers.ts`); the dev-only staff password form is impossible in production (already enforced — assert it in the smoke).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |

## Tests

- **Config check:** unit tests for every new production rule (accept good, refuse each bad value).
- **Providers:** SES/SNS/S3 clients with mocked AWS SDK calls (region, credentials chain, error mapping, retries).
- **Health:** worker liveness mechanism test; `/health` 200/503 tests stay green.
- **Images:** the smoke script above, run twice from a clean build; image sizes and `docker history` reported; a scan of the final layers for `.env`/secrets/test files.
- **Docs:** every environment variable in `.env.production.example` exists in `config.ts` (a test that compares the two lists), and the guide's variable table is generated or checked against it.
